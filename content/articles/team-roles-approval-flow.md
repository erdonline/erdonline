## 开场：个人工具上的「团队流程」

用 dbdiagram 或 draw.io，权限模型通常是：**谁有编辑链接谁就能改**。小团队凑合；一旦要对齐「谁能动生产库对应的设计、谁审批 DDL、改崩了怎么追责」，就会退化成飞书截图 + DBA 口头 OK——**模型在工具里，规矩在群聊里**。

[ERD Online](https://github.com/erdonline/erdonline) 面向团队项目提供**三级角色**与 **SQL 审批流**：设计变更先 version diff 可见，落库前可经审批人把关，权限与项目成员绑定，而不是单一分享密码。

## 三级角色：谁管什么

每个团队项目内置三层（`roleCode` 后缀 `_0` / `_1` / `_2`）：

| 角色 | 典型职责 |
|---|---|
| **团队所有者** | 项目归属、最高配置；成员与角色分配 |
| **团队管理员** | 日常管理、权限配置、审批参与 |
| **团队普通成员** | 参与建模、提交变更；敏感操作受权限码约束 |

在「用户组 / 权限配置」页可细调 privilege（如谁能改数据源、谁能导出 DDL）。非成员无法进设计器 SocketIO 房间（连接会被拒绝）——协作不是「知道 URL 就能进」。

> 诚实说明：权限模型偏「项目 + 用户组」，不是企业级 IAM 全量替换；与 LDAP/OIDC 联邦的边界见 [ADR-0021]({{DOC:adr/0021-idp-federation-google-wechat}})，默认仍是产品内账号体系。

## SQL 审批流：从 diff 到落库

典型路径：

1. 成员在设计器改模型，**保存版本**（建议每次非空 diff 都存）。
2. 版本页对目标库生成变更 SQL，行内 **「提交工单」** → 详情里 **「SQL 审批」**。
3. 选择审批人、目标数据源、说明；审批人在「我的审批」通过或拒绝。
4. **通过路径有信任链**：SQL 执行失败不会标记为已通过、不会假同步。

这与「个人工具导出 SQL 自己跑」的区别在于：**谁提、谁批、哪一版模型、哪条 SQL** 留在系统里，而不是 DBA 邮箱里一封没上下文的 `.sql`。

设计器顶栏另有 **「我的工单 / 待审批 / 通知」** 直达入口，避免审批流藏在三级菜单里找不到。拒绝后可复批；SQL 明细弹层支持键盘闭环（Esc 归还焦点），适合评审会议现场快速过一遍语句。

## 协作与版本如何配合

- **Presence + 增量 sync**：顶栏可见在线成员；他人改表会提示你保存版本，避免静默覆盖。
- **版本 diff**：评审会上直接比对两版字段/关系，而不是争论「我记得上周不是这样」。
- **只读分享**：给产品/业务看关系图，不授予编辑与审批权。

单机 ER 工具不是不能做团队流程——只是流程在外部；**我们把流程收进同一 projectJSON + 版本链**，减少「模型一套、规矩另一套」的裂缝。

## 30 秒亲手验证（免注册）

demo 以公开示例项目为主，完整审批需团队项目与 JDBC 数据源；仍可先体验权限相关的「版本 + diff」闭环：

1. 打开 demo，进入示例项目。
2. 修改一个字段 → 保存版本。
3. 打开版本管理，查看 diff；顶栏注意 presence 与「我的工单/待审批」入口位置。

自托管后创建团队项目、加成员、配数据源即可走通审批（见 [部署文档]({{DOC:deployment}})）。

## 开源与边界

MIT 开源，审批与权限**无「企业版解锁」**式阉割。SocketIO 协作需客户端能访问 9092；公网部署请配置 `ERD_UI_URL` 与 TLS 终止。
