## 开场：数据库设计缺的不是「再画一张图」

很多团队把 ER 图当成交付物：评审时画一版，上线后丢进 Confluence，下次改表靠 Navicat 直连、口头对齐、或者把 `.sql` 丢进 Flyway。工具箱里不缺「能画矩形和箭头的东西」，缺的是**把设计当成会演进、要协作、要对齐的事实源**——就像代码有 Git、界面有 Figma，数据库模型却长期停在「当前态截图 + 人肉记忆」。

[ERD Online](https://github.com/erdonline/erdonline) 的定位很直白：**数据库设计的 Git + Figma**。不是再做一个 dbdiagram 复刻，而是占住「协作化数据库设计」这条目前几乎空着的生态位。

## 生态位对照：各工具管什么、不管什么

| 工具类型 | 擅长 | 天然缺口 |
|---|---|---|
| draw.io / 通用画图 | 快速出图、形状自由 | 不懂外键语义；无版本链；改完即覆盖 |
| dbdiagram 等极简建模 | 当前模型 + DBML 导出 | 版本叙事、团队权限、自托管不是主路径 |
| Navicat 等客户端 | 连库、逆向、执行 DDL | 管的是**库实例**，不是设计阶段的协作与 diff |
| 纯迁移脚本（Flyway 等） | 已落库变更历史 | 管执行后的 DDL，不是 ER 语义与字段级设计 diff |

我们的取舍：**画布体验是及格线**（ReactFlow 关系图、DBML 导入、四库逆向），**版本 + 协作才是壁垒**——每次有意义的改动可存版、任意两版可 diff、团队在同一 projectJSON 上并行改，而不是文件传来传去。

## Git 心智：设计变更也要可追溯

建模工作流里，「保存版本」是常规动作，不是导出文件的额外步骤：

1. 在项目里改表——增删字段、调类型、拉关系，画布与 projectJSON 同步。
2. 点「保存版本」——填版本号与说明，当前模型打快照。
3. 版本列表按时间排列——选任意两版，diff 面板展示表/字段/关系级变更。

这和 Git commit 一致：**工作区可以乱改，落盘的是不可篡改的快照链**。快照存的是结构化 projectJSON，不是一堆难以比对的 SQL 文本。

> 诚实说明：空 diff 的存版可作书签，但不计入我们关注的「有效版本保存」——鼓励「改动了再存」，而不是刷版本号。

## Figma 心智：多人同屏改同一份模型

团队场景里，设计器顶栏有 presence 与增量 sync 提示：成员 A 改了表，成员 B 会看到变更提醒，落盘仍走「保存版本」——变更通过版本链汇聚，而不是 `.vsdx` 或截图来回发。

- **SocketIO 协作**（端口 9092，与 HTTP 9502 分离）：须是项目成员且客户端能连到该端口；自托管时防火墙/Nginx 要放行。
- **只读分享**：生成链接给评审方看图，不等同于编辑权限。
- **三级角色 + 审批流**：所有者 / 管理员 / 普通成员分工；结构变更可走 SQL 审批后再同步（团队场景见专门文章）。

单机工具能画得很漂亮，但**「谁在线、谁改了什么、能不能落版」**是另一套问题。

## 30 秒亲手验证（免注册）

不用注册、不用装客户端：

1. 打开 demo，进入示例项目设计器。
2. 任选一张表，新增或修改一个字段。
3. 点「保存版本」，填版本号；打开版本管理，选两版看 diff 面板。

## 开源、自部署与开放格式

- **许可**：MIT，可商用、可 fork、可内网部署。
- **一键起栈**：`docker compose up -d`，MySQL + Redis + 前后端（GHCR 预构建镜像，见 [部署文档]({{DOC:deployment}})）。
- **开放 projectJSON**：schema 版本化，承诺加法演进——脚本、Agent、MCP 可读同一份事实源。
